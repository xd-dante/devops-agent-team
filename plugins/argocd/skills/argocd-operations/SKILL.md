# GitOps Operations

Applications are generated by infrastructure code and frequently have
automated sync **off**. Those two facts explain most reports that reach this
skill: a merged change deploys nothing until someone syncs, and a pinned
target revision means it may not deploy even then.

**Read-only by default.** The one mutating action is gated behind explicit
approval and a shown diff.

## Capabilities

| Capability | Action | Description |
|------------|--------|-------------|
| App Health Triage | `actions/app-health-triage.md` | Interpret sync, health, revision and operation state together |
| Desired vs Live | `actions/desired-vs-live.md` | "My value isn't taking effect" — classify the path, locate the gap |
| Revision Pin | `actions/revision-pin.md` | "Synced but my change isn't deployed" |
| Sync Application | `actions/sync-application.md` | **Gated, mutating.** Show the diff, sync one app, verify the workload |

## Principles

1. **Git is the source of truth** — never edit a managed resource, and never
   edit the Application that infrastructure code owns.
2. **Out of sync is often normal** — where automated sync is off, it is the
   expected state after a merge.
3. **Synced does not mean deployed** — it means matching the target revision,
   which may be a pin.
4. **Classify the value path before diagnosing drift** — static values bypass
   module value shaping entirely.
5. **A diff precedes every sync** — an app out of sync for a while carries
   other people's merged changes.
6. **Every finding gets an owner.**

## Usage

1. Load this manifest and `standards/gitops-rules.md`.
2. Resolve the cluster and echo it back.
3. Execute the capability's action file.
4. Validate against `standards/checklist.md` before reporting or syncing.
